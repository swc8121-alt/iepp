# IEPP A3 VirtualBox 시험 결과 및 후속 검증 기록

작성일: 2026-09-14 · 연구자: 서우철 · 범위: 제공된 원본 로그와 실행 화면

확보한 5개 시험 사례의 클라이언트 기록 9건에서 예상한 승인·차단 결과를 확인했다. 두 분기를 제출한 4개 시험은 각각 한 분기만 승인됐으며, 별도 과거 스냅샷 복원 후 제출 1건은 차단됐다. 공유 챌린지 시험은 서버 기록과도 일치한다. 이는 소규모 기능 검증이며 전체 A3 시험 행렬 또는 L2 검증 완료를 뜻하지 않는다.

## 1. 결과표

| 시험 ID | 조건 | 승인 | 차단 사유 | 증거 범위 |
|---|---|---|---|---|
| S1-0001 | 분기별 새 챌린지, A→B | A | B: ROLLBACK_OR_LOSING_FORK | 클라이언트 원문 2건·실행 화면 |
| S1-0002 | 분기별 새 챌린지, B→A | B | A: ROLLBACK_OR_LOSING_FORK | 클라이언트 원문 2건·실행 화면 |

9건 모두 transport_ok=true, transport_error=null이다. 승인 4건은 EXECUTED_SIMULATED, 거절 5건은 BLOCKED로 기록됐다. 이는 실제 외부 서비스의 보호 동작을 실행한 증거가 아니라 하네스의 모의 동작 결과다.

## 2. 환경과 실행 버전

한 대의 Windows 노트북에서 VirtualBox와 Ubuntu VM을 사용했다. 서버는 Windows에서, 클라이언트는 Ubuntu에서 실행했다. 환경 정보는 실행 화면과 대화에서 수집한 것이며 별도 장비 감사 결과가 아니다.

| VM | SSH 로컬 포트 | Host-only IPv4 | 역할 |
|---|---|---|---|
| IEPP-Node1 | 2222 | 192.168.56.10 | 초기 A·실제 복원 시험 |
| IEPP-Node2 | 2223 | 192.168.56.11 | 초기 B |
| IEPP-Node3 | 2224 | 192.168.56.12 | 공유 챌린지 A |
| IEPP-Node4 | 2225 | 192.168.56.13 | 공유 챌린지 B |

Node1~4의 git 확인 화면에서 공통 커밋 a8a5ef374afb18f2c8a7014641fa9fad33fdb26d와 변경 출력이 없는 상태를 확인했다. Node3·4의 최신 화면은 0a90903b-8db6-4c96-8192-0f89a50bdfd7.png다. 시험 로그의 iepp_source_revision=UNKNOWN은 변경하지 않고 이 화면을 보조 증거로 둔다. 시험 후 git 상태 확인만으로 실행 당시의 모든 파일·환경까지 암호학적으로 보증하지는 않는다. Windows 서버 코드의 정확한 파일 해시는 아직 수집하지 않았다.

Ubuntu 클라이언트 런타임은 Python 3.12.3이다. 복제된 VM의 hostname은 모두 iepp-node1로 남아 있어 hostname만으로 분기를 식별하지 않는다.

## 3. 스냅샷·복원 범위

초기 S1_AFTER_P0_BEFORE_CHALLENGE 스냅샷에서 Node2를 복제했다. S1-0002와 S1-0003은 기존 VM에 새 시험 상태를 전달한 실행이며 각 사례마다 새 VM 복원을 수행한 것으로 계산하지 않는다.

RESTORE-0001에서는 Node1을 종료하고 S1_AFTER_P0_BEFORE_CHALLENGE로 실제 복원했다. Windows 레지스트리의 승인된 head는 유지됐다. 복원된 과거 상태에서 새 챌린지를 받아 제출했지만 차단됐고, head는 기존 S1-0001의 A 상태에 머물렀다.

공유 챌린지 단계에서는 Node3에서 챌린지를 발급받은 뒤 종료하고 S2_AFTER_CHALLENGE_04B 스냅샷을 생성했다. 해당 스냅샷에서 Node4를 복제했다. 두 VM의 a3-shared-challenge-04b.json SHA-256 일치는 화면으로 확인했다. 이 단계는 발급 후 스냅샷·복제 사례이며, 공유 챌린지가 사용된 뒤 명시적인 snapshot restore를 실행한 사례는 아직 없다. 로그의 challenge_issued_before_restore=true만으로 실제 restore 수행을 주장하지 않는다.

공유 상태 파일의 화면상 SHA-256:
642ff92b7648bac005e8574f80e33c19ff9ea6cb49e59f5acba795cd9f11cddf

이 파일에는 시험용 비밀키가 포함되므로 보고서에는 내용 자체를 포함하지 않았다.

## 4. 공유 챌린지의 서버·클라이언트 대조

registry-events.jsonl에는 챌린지 발급 2건과 전이 판정 2건이 있다. 최초 챌린지는 준비 중 만료된 것으로 앞선 실행 과정에서 파악됐으며 이번 제출 결과에 사용된 것은 재발급된 04b 챌린지다. 이 서버 로그에는 최초 챌린지를 제출한 판정이 없다.

현재 사용한 challenge_id:
970aeb0c60e58d0715dc09ebb25ba3b597214dbf7edea470a923c2110fef1e14

| 서버 시각 UTC | 이벤트 | 결과 |
|---|---|---|
| 2026-09-14 01:24:41.055960 | CHALLENGE_ISSUED | TTL 3,600초 |
| 2026-09-14 01:44:53.189818 | A 판정 | CONTINUITY_VALID, counter=1 |
| 2026-09-14 01:45:01.235281 | B 판정 | CHALLENGE_USED, counter=1 유지 |
| 2026-09-14 02:24:41 | 챌린지 만료 시각 | 두 판정 모두 만료 이전 |

두 판정의 evidence_id, candidate_successor, presented_predecessor, canonical_head_before/after, 승인 여부와 사유를 클라이언트 원문과 대조했고 모두 일치했다. 마지막 head 조회 화면에서도 counter=1과 A의 상태를 확인했다.

최종 head:
5e9a4953df5624f11bdf39cc1ca5aea373141cdb3f1793e9b67bdd7c1f33ea87

서버 판정 간격은 8.045463초다. 이번 공유 챌린지 시험은 순차 제출이며 동시 경쟁 시험으로 분류하지 않는다. 서버와 VM의 시계가 다르므로 서로 다른 장비의 시각 차이로 네트워크 지연을 산출하지 않는다. S1-0003의 VM 클라이언트 전송 시각 차이 43,134ns 또한 서버에서 실제 요청 처리가 겹쳤다는 증거가 아니다.

## 5. 이 결과가 뒷받침하는 주장

동일 자격증명과 이전 상태를 가진 분기들이 단일 온라인 레지스트리에 제출할 때, 관측한 네 개의 두 분기 시험에서는 승인된 후속 상태가 한 개로 유지됐다. 레지스트리가 진행한 뒤 VM을 과거 상태로 복원한 별도 시험에서도 과거 계보의 제출이 차단됐다. 공유 챌린지까지 복제한 순차 시험에서는 두 번째 사용이 차단됐다.

증거 범위는 L1 single online registry with cooperative policy gate다. B가 먼저 제출한 S1-0002에서 B가 승인됐으므로 물리적·내재적 원본을 식별했다는 결론을 내릴 수 없다. 결과는 레지스트리를 기준으로 승인된 계보가 한 개로 유지된다는 기능을 뒷받침한다.

entropy_health_status=NOT_EVALUATED이므로 물리 엔트로피 품질·예측 불가능성·TRP 난이도를 실증한 자료로 사용하지 않는다. 결과 로그의 signature_present=true는 서명 존재 기록이며, 이번 로그 대조는 서명 원문을 독립적으로 암호 검증한 절차가 아니다. 악성 하이퍼바이저, 레지스트리 자체 롤백, 다중 레지스트리 합의, 보호 게이트 우회 및 L2 하드웨어 보장은 미검증이다. 표본 수가 작아 실패 확률 또는 성공률의 일반화도 하지 않는다.

## 6. 남은 검증과 완료 기준

| 우선순위 | 남은 항목 | 필요한 증거·완료 기준 |
|---|---|---|
| 1 | 초기 세 시험·실제 복원 시험의 서버 로그 확보 | 기존 파일을 보존하여 클라이언트 evidence_id와 승인 사유 대조 |
| 1 | 실행 provenance 보완 | Windows 서버 및 VM의 실행 파일 해시·버전 수집; 기존 UNKNOWN 로그는 유지 |
| 2 | 공유 챌린지 B→A 및 공통 시각 제출 | 새 시험 ID·유효한 새 챌린지·분리된 결과 파일; 각각 한 번 승인, 후속 head 일치 |
| 2 | 공유 챌린지 사용 후 실제 restore | 레지스트리를 유지하고 VM만 복원한 기록, 유효기간과 사용 여부를 구분한 서버 거절 증거 |
| 2 | 동시 경쟁 및 반복 범위 확정 | 서버에서 요청 수신·처리 순서를 관측할 수 있는 기록과 사전 결정한 반복 수; 이중 승인 0건을 표본 수와 함께 보고 |
| 3 | L2 진입 조건 확정 | 프로젝트의 L2 정의에 맞춰 신뢰 경계, 비복제 키·하드웨어 상태, 공격자 권한과 판정 기준 명시 |
| 3 | 엔트로피 장애·침해 후 회복 | A4/A5와 별도 구분하여 정상·실패·회복 조건의 시험 설계 |

이 목록은 현재 증거의 빈틈을 기준으로 정리한 후속안이다. 이후 Issue #6 및 고정 커밋의 A3 실행서를 대조했으며, 승인 전이 이후 스냅샷·정상 연속 실행·통제 경쟁 조건도 추가로 남아 있다. 구체적인 완료 조건은 NEXT_STAGE_KO.md를 따른다. A3 전체 완료율은 숫자로 표시하지 않는다. L2 예산 상한 3만원은 유지하며 이번 정리 작업에서는 구매나 유료 자원 실행을 하지 않았다.
